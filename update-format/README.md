# Формат обновления прайсов PRO OPTIMA

Этот формат нужен для сценария:

1. Вы присылаете в ChatGPT новый прайс существующего или нового поставщика.
2. ChatGPT сопоставляет позиции с текущим `supplierCatalog`, сохраняет стабильные ID там, где товар тот же, определяет новые/исчезнувшие позиции и связи с нашими товарами.
3. ChatGPT отдаёт `PRO_OPTIMA_UPDATE_....json`.
4. В Admin: **Настройки → Обновление прайсов / предложений → Применить UPDATE**.
5. Admin сначала загружает свежую базу с Railway и делает локальный **preflight**: проверяет revision, ссылки ID, дубликаты, цены и структуру файла, ничего не записывая.
6. После подтверждения Admin отправляет только разрешённые разделы (`suppliers`, `products`, `supplierCatalog`, `offers`) через revision-защищённый PATCH. Railway отклоняет конфликт версии, делает резервную копию и записывает базу атомарно.

UPDATE **не включает в PATCH и поэтому не заменяет**:
- историю заявок;
- остатки;
- перемещения;
- запросы дат;
- общие настройки;
- старые исполненные заявки.

## Обязательные правила безопасности

`baseRevision`
: обязательный номер revision рабочей базы, по которой был подготовлен UPDATE. Если база изменилась после подготовки файла, сервер вернёт конфликт и ничего не применит. Значение `0` в шаблоне — только заглушка; перед выдачей готового UPDATE его нужно заменить на актуальную revision Railway.

`allowOperationalPatches`
: обычно `false`. Ставить `true` можно только если UPDATE намеренно меняет `orderSuppliers`, `orderSupplierByBranch`, `procurementDefault` или `procurementByBranch`. Обычный новый прайс не должен включать такие изменения автоматически.

Перед записью Admin строго проверяет ID поставщиков, товаров и каталога, дубликаты, цены и принадлежность `catalogItem` к поставщику. Затем Railway ещё раз проверяет `baseRevision`. Ошибочный или устаревший UPDATE не записывается.

Позиции из `catalogRetireIds` получают `availability = unavailable`; связанные рабочие строки в `offers` удаляются, поэтому такая позиция больше не участвует в автоподборе поставщика. Сама строка каталога сохраняется для истории и может быть восстановлена следующим прайсом с тем же стабильным ID.

## Поля

`suppliersUpsert`
: новый поставщик или изменение карточки существующего.

`catalogUpsert`
: позиции каталога поставщика. Для совпавшего товара желательно сохранять старый `id`, чтобы связи не рвались.

`catalogRetireIds`
: позиции, которых больше нет в новом прайсе. Они не удаляются, а получают `availability = unavailable`.

`catalogLinks`
: связь позиции каталога с нашим товаром (`usedProductId` + `product.catalogLinks`).

`productPatches`
: точечные изменения наших товаров: catalogLinks, выбранный заказник, branch-настройки, аналоги наших товаров.

`offersUpsert`
: рабочие строки цены/единицы, участвующие в сравнении и формировании заявок.

## Правило для новых прайсов

Непривязанные позиции остаются только в `supplierCatalog` и показываются в Admin → **Предложения**.
Они не становятся «нашими товарами» автоматически.

Для совпавшей позиции всегда сохраняем существующий `catalogUpsert[].id`. Новый ID создаём только для действительно новой позиции. Исчезнувшие строки прайса перечисляем в `catalogRetireIds`, а не удаляем.

Обычный UPDATE прайса должен менять только поставщика/каталог/цены/связи, которые прямо следуют из нового прайса. Не включаем изменения графиков поставок, истории, остатков или настроек закупки без отдельного явного решения.
